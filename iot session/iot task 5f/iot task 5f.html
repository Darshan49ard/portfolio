IoT Session — Task 5: Forge Firebase & Real-Time Integration

1. Overview

Objective

The objective of this task is to turn the ESP32 into a complete cloud-connected environmental station. A DHT11 (temperature and humidity) and an LDR (light) feed data through the ESP32 into a Firebase Realtime Database, and that data arrives live on the Task 4 web dashboard. The dashboard can also control a relay-switched bulb in manual or automatic mode.

Problem Being Addressed

In Task 4, the dashboard was built on its own with no hardware connected, so the cards showed -- and the status said Waiting. In Task 2, the ESP32 was controlled through Adafruit IO, but only in one direction (dashboard to LED), with no sensor data coming back.

This task closes the loop. Real sensor readings travel from the ESP32 to the cloud and onto the dashboard, and commands travel back from the dashboard to the ESP32 and the bulb.

Project Summary

The task is built in three parts:

  • 5.1 Sensors & Relay: wire the DHT11, LDR and relay, average the noisy light reading over 15 samples, and prove automatic relay logic on the bench.
  • 5.2 Firebase Backend: create the Firebase project, authentication, a flat database schema, security rules, the final firmware and optional cloud functions.
  • 5.3 Integration: put the real Firebase settings into the Task 4 dashboard and check the whole chain end to end.

Basic operation:

DHT11 + LDR → ESP32 → Firebase Realtime Database → Web Dashboard

                ▲                                        │

                └────────── Relay / Bulb ◄── Controls ───┘

2. Concepts

Forge

The name of the system built across Tasks 4 and 5: an ESP32 that monitors the room 24/7, syncs to the cloud, and switches a real bulb from a live dashboard.

Environmental Station

The ESP32 reading temperature and humidity from a DHT11 and ambient light from an LDR, with the same relay from Task 2 controlling the bulb.

DHT11

A digital temperature and humidity sensor. It sends its numbers as digital data and needs at least two seconds between reads. It also drifts quietly unless readings are averaged.

LDR

Light-dependent resistor. Its resistance changes with the light falling on it, so it turns brightness into a voltage the ESP32 can read.

Digital and Analog Sensors

A digital sensor (DHT11) hands over ready-made numbers. An analog sensor (LDR) gives a voltage that changes smoothly, and the ESP32 has to measure it.

ADC

Analog-to-digital converter: the part of the ESP32 that turns a voltage into a number. It is 12-bit, so it reads 0–4095. An Arduino's is 10-bit (0–1023), so thresholds copied from an Arduino would be off scale.

Noise

Readings that jump for no reason. The raw light value went 500, then 2000, then 300.

15-Sample Averaging

Instead of trusting one reading, take 15 readings 8 ms apart and use their average. It gave a stable value, and better accuracy than the hardware filter capacitor first considered.

Capacitor (Hardware Filter)

A small component that smooths a signal. It was the first idea for the noise, but it is inflexible; averaging in software is easier to change.

Manual Override

The bulb follows the toggle on the dashboard, whatever the light is doing.

Automatic Mode

The ESP32 decides on its own by watching the light and switching the bulb when the light crosses a threshold.

Threshold

The light level, from 0 to 4095, at which automatic mode switches the bulb. It can be tuned from the dashboard.

Data Point

One reading of temperature, humidity, light and relay state. One every two seconds is 43,200 data points a day.

Sync

Getting the data to the cloud. Testing showed steady readings, about a 1–2 second sync, and a relay response of around 10 ms.

Default OFF

If anything disconnects, the relay goes back to OFF.

Firebase

Google's cloud platform for apps. Here it stores the data, signs users in and keeps everything in sync. Every reading, bulb state and mode change flows through it in real time.

Realtime Database

Firebase's database for live data. It stores everything as one big tree of JSON, and connected devices are told about changes within a moment.

NoSQL

A database without tables, rows and joins. Nested data is stored and read by its path.

Flat Schema

Keeping the data shallow: a few top-level paths instead of deep nesting. A deeply nested first design made queries crawl; flattening it made them instant.

Timestamp Key

Each reading is stored under the time it was taken, so readings are naturally in order.

Authentication

Proving who a user is. Forge signs users in with email and password or with Google Sign-In.

Security Rules

The rules that decide who can read or write each path. Every user can only read their own data, and readings can only be written by the firmware.

Cloud Functions

Small programs that run in the cloud when something happens. Forge uses them to archive readings older than 30 days, raise an alert above 40 °C, keep an audit trail of every bulb command, and serve history to the dashboard.

Audit Trail

A permanent log of who did what and when. Here it records every bulb command.

Firestore

Firebase's other database, better for complex per-user documents. It was not the right fit for a stream of time-series readings.

Latency

The delay between something happening and its result appearing. Reads take 50–200 ms and streams update in under a second.

Integration and End-to-End Testing

Integration means joining parts that were built and tested separately (sensors and relay, Firebase backend, dashboard) so they work as one system. End-to-end means every link is checked together in one pass.

Real-Time Listener

Code that is called the moment a value changes, so a change on the hardware appears on the dashboard within about a second, with no refresh and no polling.

Firebase Hosting

Firebase's free web hosting, used to put the finished dashboard on a public address.

3. System Design

System Architecture

The complete system contains six major elements:

Sensors → ESP32 → Firebase Realtime Database → Web Dashboard → User

                        ▲                            │

                        └── Controls (bulb, mode, threshold)

                                  │

                              ESP32 → Relay → Bulb

Data Flow

Every 2 seconds the ESP32 performs this cycle:

  1. Reads the controls from Firebase (bulb, mode, threshold).
  2. Reads the DHT11 and the averaged LDR value.
  3. Switches the relay: in manual mode it follows the dashboard toggle, in automatic mode it compares light to the threshold.
  4. Writes one reading (temperature, humidity, light, relay) to Firebase, keyed by its timestamp.
  5. The dashboard's real-time listeners receive the new reading and redraw the cards, status line and history table.

If WiFi or Firebase is lost, the relay falls back to OFF.

5. Firebase Account and Configuration

Step 1 — Create the Firebase Project

At console.firebase.google.com, sign in with a Google account, choose Create a project, name it (for example forge), turn Google Analytics off, and press Create project.

Step 2 — Create the Realtime Database

Open Build → Realtime Database → Create Database, choose the closest location and start in locked mode. Copy the database address shown at the top of the Data tab (it looks like https://forge-default-rtdb.firebaseio.com, or ends in firebasedatabase.app).

Step 3 — Turn On Sign-In

Open Build → Authentication → Get started → Sign-in method. Enable Email/Password, then add the Google provider, choose a support email, and Save.

Step 4 — Create Two Users

In the Users tab, add two users:

Used to sign in to the dashboard; its User UID is copied for the firmware

Device account (e.g. forge-device@example.com)

Used by the ESP32 only; the email does not need to be real

Two accounts is what lets the security rules say "only the device can write readings".

Step 5 — Copy the Web Settings

Open Project settings → General → Your apps, press the web icon </>, register the app and copy the firebaseConfig block. The apiKey in it is also the key the ESP32 uses.

8. Communication Flow

The complete communication process is:

Sensors ──► ESP32 ──► Firebase ──► Dashboard ──► User

                         ▲             │

                         └─── Controls ┘

                                │

                                ▼

                         ESP32 ──► Relay ──► Bulb

Example — Live Reading

DHT11 / LDR read by ESP32

       ↓

ESP32 writes reading under users/<uid>/readings/<unix time>

       ↓

Firebase Realtime Database

       ↓

Dashboard real-time listener fires

       ↓

Cards, status line and history table update (about 1–2 s)

Example — Manual Bulb ON

User flips the toggle ON

       ↓

Dashboard writes bulb = true

       ↓

ESP32 reads bulb on its next cycle

       ↓

RELAY_ON → bulb lights

Example — Automatic Mode

User selects Automatic

       ↓

Dashboard writes settings/mode = "auto"

       ↓

ESP32 compares averaged light with threshold

       ↓

Light above threshold → relay ON, otherwise OFF

Example — Connection Lost

WiFi or Firebase disconnects

       ↓

ESP32 sets relay OFF (safe default)

       ↓

Dashboard status changes from Live to Waiting

       ↓

Connection returns → readings resume by themselves

Security Rules (database.rules.json)

{

  "rules": {

    "users": {

      "$uid": {

        ".read": "auth != null && (auth.uid === $uid || auth.token.email === 'YOUR_DEVICE_EMAIL')",

        "bulb": {

          ".write": "auth != null && auth.uid === $uid",

          ".validate": "newData.isBoolean()"

        },

        "settings": {

          ".write": "auth != null && auth.uid === $uid",

          "mode": { ".validate": "newData.isString() && (newData.val() === 'manual' || newData.val() === 'auto')" },

          "threshold": { ".validate": "newData.isNumber() && newData.val() >= 0 && newData.val() <= 4095" }

        },

        "readings": {

          ".write": "auth != null && auth.token.email === 'YOUR_DEVICE_EMAIL'"

        }

      }

    }

  }

}

In plain words: a user can read only their own branch (and the ESP32 account can read it too, to fetch the controls). Only that user can change the bulb and settings, and values are validated so nothing odd can be stored. Only the ESP32 account can write readings, so sensor data can never be typed in by hand.

Testing the Rules

In Realtime Database → Rules → Rules Playground:

  • A read at /users/someone-elses-id while authenticated as yourself should be denied.
  • A read at /users/<your user id> should be allowed.

10. Implementation

Part 5.1 — Hardware Test Code (No WiFi, No Cloud)

Install DHT sensor library by Adafruit (choose Install all for dependencies), then upload:

/* Task 5.1 - Forge hardware test

   Reads the DHT11 (temperature + humidity) and the LDR (light), averages the

   light over 15 samples, and switches the relay on its own when the light

   reading is above a threshold. Everything is printed to the Serial Monitor.

   No WiFi and no cloud yet - this proves the hardware first. */

#include <DHT.h>

const int DHT_PIN   = 4;       // DHT11 data

const int LDR_PIN   = 34;      // LDR divider (an ADC1 pin, so it also works once WiFi is on)

const int RELAY_PIN = 26;      // relay module IN

const int RELAY_ON  = LOW;     // swap if your relay module is the opposite (see Task 2)

const int RELAY_OFF = HIGH;

const int SAMPLES       = 15;  // readings averaged into one light value

const int SAMPLE_GAP_MS = 8;   // pause between two samples

int threshold = 2000;          // 0-4095: relay ON above this light reading (tune it later)

DHT dht(DHT_PIN, DHT11);

int readLightAveraged() {

  long sum = 0;

  for (int i = 0; i < SAMPLES; i++) {

    sum += analogRead(LDR_PIN);

    delay(SAMPLE_GAP_MS);

  }

  return sum / SAMPLES;

}

void setup() {

  Serial.begin(115200);

  digitalWrite(RELAY_PIN, RELAY_OFF);      // start in the safe OFF state

  pinMode(RELAY_PIN, OUTPUT);

  dht.begin();

}

void loop() {

  float temperature = dht.readTemperature();   // degrees C

  float humidity    = dht.readHumidity();      // percent

  int lightRaw      = analogRead(LDR_PIN);     // one single reading: jumpy

  int light         = readLightAveraged();     // 15 readings averaged: steady

  bool relayOn = light > threshold;

  digitalWrite(RELAY_PIN, relayOn ? RELAY_ON : RELAY_OFF);

  if (isnan(temperature) || isnan(humidity)) {

    Serial.println("DHT11 read failed - check the wiring");

  } else {

    Serial.printf("Temp %.1f C | Humidity %.0f %% | Light raw %d -> averaged %d | Relay %s\n",

                  temperature, humidity, lightRaw, light, relayOn ? "ON" : "OFF");

  }

  delay(2000);                                 // the DHT11 needs at least 2 s between reads

}

Expected Serial Monitor output:

Temp 27.4 C | Humidity 58 % | Light raw 2210 -> averaged 1934 | Relay OFF

Part 5.2 — Final Firmware (Sensors + Relay + Firebase)

Install Firebase Arduino Client Library for ESP8266 and ESP32 by Mobizt. Fill in seven values at the top: WiFi name and password, the apiKey, the database address, the device account's email and password, and your own User UID.

/* Task 5.2 - Forge firmware (sensors + relay + Firebase)

   Every 2 seconds the ESP32:

     1. reads the controls from Firebase  (bulb, mode, threshold)

     2. reads the DHT11 and the averaged LDR

     3. switches the relay (manual = follow the dashboard toggle, auto = light vs threshold)

     4. writes one reading (temperature, humidity, light, relay) keyed by its timestamp

   If WiFi or Firebase is lost, the relay falls back to OFF. */

#include <WiFi.h>

#include <time.h>

#include <DHT.h>

#include <Firebase_ESP_Client.h>

#include <addons/TokenHelper.h>

// ---------- fill these in ----------

#define WIFI_SSID       "YOUR_WIFI_NAME"

#define WIFI_PASSWORD   "YOUR_WIFI_PASSWORD"

#define API_KEY         "YOUR_FIREBASE_WEB_API_KEY"

#define DATABASE_URL    "https://YOUR-PROJECT-default-rtdb.firebaseio.com"

#define DEVICE_EMAIL    "YOUR_DEVICE_EMAIL"        // the second user you created for the ESP32

#define DEVICE_PASSWORD "YOUR_DEVICE_PASSWORD"

#define OWNER_UID       "YOUR_OWN_USER_UID"        // the UID of YOUR account (the dashboard login)

// -----------------------------------

const int DHT_PIN   = 4;

const int LDR_PIN   = 34;

const int RELAY_PIN = 26;

const int RELAY_ON  = LOW;               // swap if your relay module is the opposite

const int RELAY_OFF = HIGH;

const int SAMPLES               = 15;    // light readings averaged into one value

const int SAMPLE_GAP_MS         = 8;

const unsigned long CYCLE_MS    = 2000;  // one reading every 2 s = 43,200 a day

DHT dht(DHT_PIN, DHT11);

FirebaseData fbdo;

FirebaseAuth auth;

FirebaseConfig config;

String base = String("/users/") + OWNER_UID;   // everything lives under your own user id

bool   bulbWanted = false;                     // the dashboard toggle

String mode       = "manual";                  // "manual" or "auto"

int    threshold  = 2000;                      // 0-4095

bool   relayOn    = false;

unsigned long lastCycle = 0;

void setRelay(bool on) {

  relayOn = on;

  digitalWrite(RELAY_PIN, on ? RELAY_ON : RELAY_OFF);

}

int readLight() {

  long sum = 0;

  for (int i = 0; i < SAMPLES; i++) {

    sum += analogRead(LDR_PIN);

    delay(SAMPLE_GAP_MS);

  }

  return sum / SAMPLES;

}

void connectWiFi() {

  Serial.print("Connecting to WiFi");

  WiFi.mode(WIFI_STA);

  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);

  while (WiFi.status() != WL_CONNECTED) {

    delay(500);

    Serial.print(".");

  }

  Serial.println();

  Serial.println("WiFi connected");

}

void setup() {

  Serial.begin(115200);

  digitalWrite(RELAY_PIN, RELAY_OFF);      // safe OFF from the very first moment

  pinMode(RELAY_PIN, OUTPUT);

  dht.begin();

  connectWiFi();

  // The reading's key is the current time, so the clock must be right first.

  configTime(0, 0, "pool.ntp.org", "time.nist.gov");

  Serial.print("Syncing the clock");

  while (time(nullptr) < 1700000000) {

    delay(300);

    Serial.print(".");

  }

  Serial.println();

  config.api_key      = API_KEY;

  config.database_url = DATABASE_URL;

  auth.user.email     = DEVICE_EMAIL;

  auth.user.password  = DEVICE_PASSWORD;

  config.token_status_callback = tokenStatusCallback;   // prints sign-in progress

  Firebase.reconnectWiFi(true);

  Firebase.begin(&config, &auth);

}

void loop() {

  if (millis() - lastCycle < CYCLE_MS) return;

  lastCycle = millis();

  if (WiFi.status() != WL_CONNECTED) {

    setRelay(false);                       // no network: safe OFF

    connectWiFi();

    return;

  }

  if (!Firebase.ready()) {

    setRelay(false);                       // not signed in yet: safe OFF

    return;

  }

  // 1. controls from the dashboard (if one read fails we simply keep the last value)

  if (Firebase.RTDB.getBool(&fbdo, (base + "/bulb").c_str()))            bulbWanted = fbdo.boolData();

  if (Firebase.RTDB.getString(&fbdo, (base + "/settings/mode").c_str())) mode       = fbdo.stringData();

  if (Firebase.RTDB.getInt(&fbdo, (base + "/settings/threshold").c_str())) threshold = fbdo.intData();

  // 2. sensors

  float temperature = dht.readTemperature();

  float humidity    = dht.readHumidity();

  int   light       = readLight();

  // 3. relay

  if (mode == "auto") setRelay(light > threshold);

  else                setRelay(bulbWanted);

  // 4. one reading up to the cloud

  if (isnan(temperature) || isnan(humidity)) {

    Serial.println("DHT11 read failed - skipping this reading");

    return;

  }

  FirebaseJson reading;

  reading.set("temperature", temperature);

  reading.set("humidity", humidity);

  reading.set("light", light);

  reading.set("relay", relayOn);

  String path = base + "/readings/" + String((unsigned long)time(nullptr));

  if (Firebase.RTDB.setJSON(&fbdo, path.c_str(), &reading)) {

    Serial.printf("Sent | %.1f C | %.0f %% | light %d | relay %s | mode %s\n",

                  temperature, humidity, light, relayOn ? "ON" : "OFF", mode.c_str());

  } else {

    Serial.print("Send failed: ");

    Serial.println(fbdo.errorReason());

  }

}

Expected Serial Monitor output:

Sent | 27.4 C | 58 % | light 1934 | relay OFF | mode manual

const { onSchedule } = require("firebase-functions/v2/scheduler");

const admin = require("firebase-admin");

admin.initializeApp();

const db = admin.database();

// If your Realtime Database is NOT in the US, name its region and instance here, e.g.

// const WHERE = { region: "asia-southeast1", instance: "YOUR-PROJECT-default-rtdb" };

const WHERE = {};

// 1. Alert: write a note whenever a reading is above 40 degrees C.

exports.temperatureAlert = onValueCreated({ ref: "/users/{uid}/readings/{ts}", ...WHERE }, async (event) => {

  const reading = event.data.val();

  if (reading && reading.temperature > 40) {

    await db.ref(`/users/{event.params.ts}`).set({

      temperature: reading.temperature,

      message: "Temperature above 40 C"

    });

  }

});

// 2. Audit trail: remember every change of the bulb command.

exports.bulbAudit = onValueWritten({ ref: "/users/{uid}/bulb", ...WHERE }, async (event) => {

  await db.ref(`/users/${event.params.uid}/audit`).push({

    bulb: event.data.after.val(),

    at: admin.database.ServerValue.TIMESTAMP

  });

});

// 3. Archive: once a day, move readings older than 30 days to /archive.

exports.archiveOldReadings = onSchedule("every 24 hours", async () => {

  const cutoff = String(Math.floor(Date.now() / 1000) - 30 * 24 * 60 * 60);

  const users = await db.ref("/users").once("value");

  const jobs = [];

  users.forEach((user) => {

    jobs.push((async () => {

      const old = await db.ref(`/users/${user.key}/readings`).orderByKey().endAt(cutoff).once("value");

      const updates = {};

      old.forEach((row) => {

        updates[`/users/{row.key}`] = row.val();

        updates[`/users/{row.key}`] = null;

      });

      if (Object.keys(updates).length) await db.ref().update(updates);

    })());

  });

  await Promise.all(jobs);

});

11. Explanation of Important Code Sections

Reading the DHT11

float temperature = dht.readTemperature();

float humidity    = dht.readHumidity();

The DHT11 returns ready-made digital values. It needs at least 2 seconds between reads, which is why the loop ends with delay(2000) and the firmware uses a 2000 ms cycle.

15-Sample Averaging

int readLight() {

  long sum = 0;

  for (int i = 0; i < SAMPLES; i++) {

    sum += analogRead(LDR_PIN);

    delay(SAMPLE_GAP_MS);

  }

  return sum / SAMPLES;

}

A single analogRead jumped around (500, 2000, 300). Taking 15 readings 8 ms apart and averaging them gives a steady value, done in software so it is easy to change.

Automatic Relay Logic

if (mode == "auto") setRelay(light > threshold);

else                setRelay(bulbWanted);

In automatic mode the ESP32 decides from the light and threshold. In manual mode it simply follows the dashboard toggle.

Safe Default OFF

digitalWrite(RELAY_PIN, RELAY_OFF);      // safe OFF from the very first moment

pinMode(RELAY_PIN, OUTPUT);

...

if (WiFi.status() != WL_CONNECTED) { setRelay(false); ... }

if (!Firebase.ready())             { setRelay(false); ... }

The relay is set OFF before the pin becomes an output, and falls back to OFF whenever WiFi or Firebase is unavailable.

Clock Sync

configTime(0, 0, "pool.ntp.org", "time.nist.gov");

while (time(nullptr) < 1700000000) { delay(300); }

Each reading is stored under the time it was taken, so the ESP32's clock must be correct before it sends anything.

Firebase Sign-In

auth.user.email    = DEVICE_EMAIL;

auth.user.password = DEVICE_PASSWORD;

Firebase.begin(&config, &auth);

The ESP32 signs in with its own device account, which is what allows the security rules to let only the firmware write readings.

Reading Controls from Firebase

if (Firebase.RTDB.getBool(&fbdo, (base + "/bulb").c_str())) bulbWanted = fbdo.boolData();

The ESP32 reads the bulb, mode and threshold each cycle. If a read fails, it keeps the last known value.

Writing a Reading

String path = base + "/readings/" + String((unsigned long)time(nullptr));

Firebase.RTDB.setJSON(&fbdo, path.c_str(), &reading);

Each reading is written as one JSON object under a timestamp key, which keeps the schema flat and the readings ordered.

Dashboard Real-Time Listener

onValue(query(ref(db, base + "/readings"), limitToLast(20)), (snap) => { ... render(); }, readError);

The dashboard listens to the latest 20 readings and redraws the moment new data arrives, with no refresh and no polling.

13. Challenges & Fixes

Challenge 1 — Noisy Light Reading

Problem: The raw light value jumped from 500 to 2000 to 300 with no reason. Solution: A single reading was replaced with 15 samples spaced 8 ms apart and averaged. This gave a stable value and better accuracy than the hardware filter capacitor first considered.

Challenge 2 — DHT11 Timing and Drift

Problem: The DHT11 gave failed reads and drifted quietly. Solution: The code waits at least 2 seconds between reads, and readings stabilized once they were averaged.

Challenge 3 — ADC Range Assumption

Problem: Thresholds copied from an Arduino would be wrong, because an Arduino's ADC is 10-bit (0–1023). Solution: The ESP32's ADC is 12-bit (0–4095), so the threshold, slider and security rules all use the 0–4095 range.

Challenge 4 — Deeply Nested First Schema

Problem: The first database design nested paths deeply, and queries crawled. Solution: The data was flattened in about 30 minutes into a few top-level paths: readings keyed by timestamp, the bulb toggle, and settings for mode and threshold. Queries became instant.

14. Learning Reflection

This task taught me that reading the real world is messy. My light sensor jumped all over the place, so I stopped blaming the hardware and started averaging 15 samples spaced 8 ms apart, which gave me a smooth, trustworthy reading and proved the value of solving problems in software. The DHT11 forced me to respect its timing and drift before its readings stabilized to well under a degree. Giving the relay two modes felt like real product design: a manual button for me, and an automatic mode that watches the light threshold and switches itself, always falling back to OFF if the connection drops. I also made a habit of double-checking every spec, because assuming wrong is how silent bugs are born.

Firebase was the nervous system that tied the hardware to the screen, and it handed me my first real architecture failure. I started with a deeply nested database structure, watched the queries crawl, and spent about half an hour tearing it down into a flat layout. What made this feel like production work was the security layer: email and Google sign-in, and rules so each user only sees their own data and sensor records can only be pushed by the firmware. The real-time listeners were the satisfying part: flip the toggle on the dashboard and the hardware reacts in about a second, in both directions.

Choosing the backend forced me to think, not copy. Realtime Database won because the workload is live time-series streams from one sensor station with listeners on the dashboard, exactly what it was made for. Firestore would be better for complex per-user documents, but that is not this system.

The build order mattered as much as the stack: firmware and hardware first, then the cloud, then the UI, so that at every moment only one layer could be the unknown. That rule saved me days of frustrating guesswork.

The task improved my understanding of analog and digital sensors, ADC resolution, noise filtering, relay control, NoSQL schema design, authentication, security rules, cloud functions, real-time listeners and end-to-end integration.
